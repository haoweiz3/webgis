# 长江武汉段三维时空数据可视化平台

> 面向三维 GIS 平台研发岗位的面试作品 · Vue3 + Vite + Cesium + ECharts + Pinia

一个以长江武汉段为研究区的三维时空数据可视化平台：在真实影像与地形底座上叠加水域、岸线、跨江桥梁、主干道与监测站点等空间要素，用**时间轴驱动水位、站点与淹没范围同步变化**，并提供量算、剖面、淹没三类空间分析工具。

项目的重点不在"做一个好看的页面"，而在**用平台化的方式组织三维 GIS 功能**：统一的模块契约、事件总线、状态管理与图层注册机制，使每个功能都可以独立启停、互不干扰。

## 二、技术栈与架构

```
Vue3（组合式 API） + Vite + 原生 JavaScript
Cesium 1.97（三维引擎） + ECharts 5（图表） + Pinia（状态） + Sass（样式）
```

### 分层结构

```
引擎层   src/core/cesium/       视图工厂、相机、坐标拾取、空间计算、底图纠偏
平台层   src/core/platform/     模块契约、注册中心、上下文、事件总线
状态层   src/stores/            scene（场景）/ time（时间）/ data（业务数据）
业务层   src/modules/           11 个功能模块，全部实现同一份契约
表现层   src/components/hud/    HUD 面板与图表，全部自绘
数据层   public/data/           空间要素与时空序列数据（脚本生成）
```

### 模块契约（平台的核心）

每个功能都是一个模块，必须实现同一份约定：

```js
export default defineModule({
  id: 'water',
  name: '水域与岸线',
  group: '空间数据',
  layers: [{ id: 'layer-water', name: '水域面', group: '空间数据' }],
  init(ctx) {            // 挂载：拿到上下文，返回对外 API
    const viewer = ctx.viewer
    // …创建实体
    return { setLayerVisible(layerId, visible) { /* … */ } }
  },
  destroy(ctx, api) {    // 卸载：移除实体、解绑监听，保证可反复启停
    // …
  }
})
```

`ctx` 是模块唯一能接触到的外部世界：

```js
ctx = { viewer, camera, terrainProvider, eventBus, scene, time, data, dataService, utils, toast }
```

模块不自己 `new Viewer`、不直接 import 业务 store，因此**功能可插拔、可开关、可销毁**，配置变化只影响引擎层。

### 事件与状态的分工

- 状态（Pinia）：当前时刻、当前水位、选中站点、图层开关——需要被多个面板同时读取并响应式更新。
- 事件（eventBus）：`time:changed`、`analysis:result`、`data:stationSelected` 等一次性通知，避免模块之间相互引用。

### HUD 布局与面板导航

- 骨架尺寸集中在 `src/styles/main.scss` 的 `--hud-top / --hud-bottom / --col-left / --col-right` 变量里，小屏（1366×768 一类）由媒体查询自动收紧；栏内每个面板都有高度预算，内容超出时在面板内部滚动，不会被裁掉。
- 侧栏比例：图层面板占据剩余高度，分析面板最多占半栏（展开淹没分析时不会把图层面板挤没）；属性卡最多占 42%，其余留给站点面板。
- 顶栏的 ◀ ▶ 是应用内的返回/前进（快捷键 `[` `]`，不用 Alt + ←：那是浏览器自己的后退键，网页拦不住）。历史记录的是「选中站点 + 打开的要素属性卡」组合快照，站点详情里的"← 返回列表"也是一次可回退的操作。
- 相机飞行统一走 `src/core/cesium/camera.js`：用 `flyToBoundingSphere` + `HeadingPitchRange` 让目标点落在视图中心。早期用 `camera.flyTo({ destination })` 会把目标当相机位置，带俯仰角时中心偏出「高度 / tan|俯仰角|」——站点定位偏 2.7 km、视角书签偏 6.0 km、初始视角偏 29 km，`pnpm verify:camera` 可回归（现在都是 0.0 m）。

### 水位只有一个真值来源

`data.effectiveWaterLevel`（吴淞高程）是平台里水位的唯一真值：三维水面高度、淹没判定、站点着色、状态栏读数全部由它派生。这样"拖时间轴"和"拖水位滑块"不会出现两套状态打架。

## 三、数据说明（重要）

数据由 `scripts/build-data.mjs` 生成到 `public/data/`，口径如下：

| 数据 | 来源与口径 |
| --- | --- |
| 水域面、岸线 | **真实水系数据**：取自 OpenStreetMap（`natural=water` + `water=river`），含长江主河道、汉江下游段与 16 个江心洲，坐标 WGS-84，许可 ODbL 1.0 |
| 滩地淹没单元 | **示意单元**：沿真实岸线向外按 260 / 640 / 1150 / 1750 m 分带，高程 24.0 / 25.5 / 27.0 / 28.5 m（吴淞）为演示取值 |
| 跨江桥梁 | 本地公开整理数据，含真实经纬度与简介（武汉长江大桥、鹦鹉洲、杨泗港、白沙洲） |
| 主干道 | 从武汉路网数据中筛选国道/省道/快速路并抽稀，800 条作为空间参照 |
| 站点 | 真实站点名称与河段位置（如汉口武汉关、天兴洲、阳逻），警戒水位参考公开资料；点位由所在河段的锚点投到真实水面边界（岸边设站），锚点随数据发布以便核对 |
| 水位/流量/雨量/水质时序 | **按水文规律模拟生成**（96 小时降雨—洪水过程：面雨量峰值 9.1 mm/h、累计 186 mm → 涨水 → 洪峰 → 退水；汉口洪峰 28.39 m、超警戒 18 小时，流量峰值约 6.5 万 m³/s（按水位—流量关系曲线反算）；洪峰自上游向下游滞后 0~5 小时），仅用于演示 |

### 高程基准处理

- 站点的水位、滩地高程、警戒水位统一采用**吴淞高程**，空间分析与阈值判定都在同一基准下完成；
- 三维渲染时按固定偏移量换算为场景高程（`src/config/scene.js` 的 `DATUM_OFFSET_M`，演示取值）；
- 生产环境应使用高程基准转换模型或控制点精算，剖面高程也需与水位数据统一基准后再做淹没关系判定。

### 地形起伏的实际表现（重要口径）

地形图层用的是 ArcGIS 全球地形（`WorldElevation3D/Terrain3D`，无需 key），**服务正常、也确实生效**（状态栏"地面高程"读到的就是它的值，关掉地形会退回椭球面读 0 m）。但在长江武汉段**看不到起伏是正常的**：

- 这份全球 DEM 在武汉段的**有效格网非常粗**：沿跨龟山 2 km 断面以 20 m 间距取 101 个点，高程全部是 **24.8 m，高差 0.0 m**；汉口向西北 20 km（1 km 间距）也完全同值；
- 也就是说，真实的龟山（约 90 m）、蛇山、珞珈山以及长江河道下切，在这份数据里被整体抹平了，**放大也看不出来**。服务本身是好的：远处高差准确，实测拉萨 4959.9 m、神农架 1223.5 m、木兰山 286.3 m（真实值更高，说明同样被平滑）；
- 因此**剖面分析在研究区内接近一条水平线**（±1 m 量级），这是地理事实而不是功能故障。要展示地形能力，应把剖面线放在研究区外围的丘陵/山区，或换更高分辨率的本地 DEM（30 m 级 Copernicus / ALOS 数据）。

### 栅格法淹没分析（数据侧验证，尚未接入界面）

为了回答"淹没范围能不能由地形决定"，先用 30 m 级 DEM 做了一次数据侧验证（不改界面）：

```bash
pnpm fetch:dem      # 取 AWS 开放地形瓦片（terrarium，SRTM 30 m 派生）→ 1000×720 高程格网
pnpm analyze:flood  # 基准标定 + 逐水位栅格淹没 + 连通性 + 与示意单元法对比
```

产物在 `scripts/data-src/`：`dem-grid.bin`（1.37 MB，Uint16，0.1 m 精度）、`flood-raster-report.json`、`flood-raster-preview.png`（深蓝=河道，青蓝=连通淹没，淡黄=低于水位但未连通，白线=现有示意单元边界）。

**验证结论（三个发现）：**

1. **30 m DEM 确实带地形信息**：研究区高程 −97.6~400.3 m，武汉城区内部有 53 m 高差（河面 17 m、后湖 12 m、龟山 37 m、喻家山 65 m），与现在那份"全程 24.8 m"的全球地形完全不同，栅格法能给出地形驱动的不规则边界，不再是等宽带。
2. **但城区 DEM 是"含建筑与树冠的表面高程"**：汉口江边向西北 2 km 的横断面在 200 m 间隔上波动 ±10 m、读数比真实地面高 15~30 m（读到的是楼顶）；阳逻这类非建成区才接近真实地面。**因此用它做全城淹没会严重低估**，这类区域必须用去建筑 DEM（如 FABDEM）或叠加建成区掩膜。
3. **连通性结论比面积更值得讲**：27.3 m（警戒）时，连通淹没 266.9 km²（其中 247 km² 是河道本身，新增陆地只有 19.6 km²），而"地形上低于水位"的面积是 1474 km²——差 5.5 倍。差值主要被堤防（DEM 里能看到 1~2 m 的堤）与城区伪高值挡住。对 DEM 做 5×5 中值平滑后结果几乎不变（266.9 → 263.6 km²），说明噪声是系统性的（建筑）而不是椒盐噪声。

对照现有示意单元法：27.0 m 时单元法 375.8 km²、栅格法连通 265.5 km²、不考虑堤防的"低于水位"面积 1474 km²——单元法恰好落在两者之间，正好说明它是"既不含地形约束、也不含堤防约束"的折中口径。

**高程基准也必须显式标定**：terrarium 是 EGM96 口径，实测河面中值 16.0 m，而汉口站序列最低水位是 23.87 m（吴淞），标定偏移 **+7.87 m**。不标定直接套水位，淹没面积会整体偏大或偏小；不同 DEM 源在城区还能差 10 m 以上（后湖 SRTM 12 m vs GLO-90 23 m），所以这类面积结论必须给出区间与数据源口径，不能只报一个数。

### 数据源可得性核查（城市地面栅格与堤防高程）

| 数据 | 可得性 | 实测/说明 |
| --- | --- | --- |
| FABDEM（去建筑与树冠，30 m，做城区淹没的最优解） | ⚠️ 需免费注册 | AWS 桶存在但对象非公开（403），OpenTopography 需要免费 API key（400）；注册后可按研究区范围下载 |
| Copernicus DEM GLO-30 | ✅ 免 key | AWS 直连 `copernicus-dem-30m`，1°×1° 瓦片约 44~47 MB 且支持分段请求；但它是 **DSM**（建筑被 30 m 格网平均进去） |
| Copernicus DEM GLO-90 | ✅ 免 key | 单点查询可用，90 m 太粗，只能做趋势判断 |
| AWS terrarium（SRTM 30 m） | ✅ 免 key | 已在用；城区是"含建筑与树冠的表面高程"，实测比真实地面高 15~30 m |
| 堤防线（长江/汉江干堤、江滩绿道） | ✅ 免 key | OSM 研究区内 146 个要素，含「武昌长江大堤」「东西湖大堤」「汉江堤路」等具名要素 |
| 堤顶高程 | ❌ 无免 key 权威源 | OSM 的 146 个堤防要素**没有一条带 height/ele**；30 m 格网分辨不出 8~10 m 宽的堤，无法从 DEM 可靠反演；精化只能靠公开文献/政府文件里的堤顶高程表（需人工查证并标注精度） |

城区"是否读到地面"的实测对比（汉口江边向西北 2 km，每 200 m 一点，真实地面约 25~30 m）：

```
GLO-90 ：  26  27  35  34  31  37  21  29  23  24  28
SRTM30 ：36.3 35.8 37.3 51.4 35.8 32.1 37.2 39.8 29.3 34.5 30.1
```

GLO-90 的低值已接近真实地面，但高处仍有 35~37 m 的建筑残留；SRTM 整体偏高且波动更大。

**堤顶高程缺失的应对**：不追求精确漫堤模拟，改用「区间报数」——下界把 OSM 堤线当作不可穿越屏障（水不进城），上界不考虑堤防（凡低于水位的陆地都算），真实情况落在两者之间，并在面板与文档里写明这个口径。

### FABDEM 已接入（去建筑的城市地面高程）

在布里斯托数据页下载 `N30E110-N40E120_FABDEM_V1-2.zip` 解压后（99 个 1°×1° GeoTIFF），研究区只需 `N30E113` 与 `N30E114` 两块：

```bash
pnpm import:fabdem          # 体检：打印 TIFF 结构与研究区所需分块
pnpm import:fabdem --write  # 提取研究区 100 m 格网，覆盖 dem-grid.*（原格网另存为 dem-grid-srtm.*）
pnpm analyze:flood          # 用 FABDEM 格网跑淹没分析（--grid=srtm 可跑旧格网对比）
```

**实测格式**：3600×3600、1 弧秒像元、DEFLATE、水平差分预测器（predictor 2，按 int32 位模式差分后重新解释为 float32）、256×256 分块、`GDAL_NODATA=-9999`。解码用独立来源交叉验证过：武汉市区中心点 FABDEM 21.5 m、GLO-90 27 m。

**效果**：汉口江边向西北 2 km 的断面，FABDEM 是 21~29 m、SRTM 是 30~47 m，而真实地面 25~30 m——**城区建筑偏差已经解决**；预览图里山地纹理与连片低洼地也终于看得出来。

**但基准偏移成了新的主导误差**：城区地面集中在 22~30 m 的窄带里，整体平移几米结果就翻天覆地。27 m 水位下的连通淹没面积实测：偏移 +8.87 m（自动标定）→ **267 km²**；+5 m → 1410 km²；+2 m → 5301 km²；+1 m → 5591 km²，**20 倍摆动**。自动标定（江面 = 序列最低水位）与"城区地面 25~27 m 吴淞"这两种口径互相矛盾 4~6 m，说明 DEM 水面与模拟序列水位之间本身存在不一致。

**所以：在拿到控制量之前，不要给出单一的"淹没面积"数字。** 三条出路：① 用公开文献里的堤顶高程表；② 用已知地面点高程；③ 改用"水位相对基准水面的抬升量"这一自洽口径（推荐，完全避开绝对基准问题）。

### 相对口径与堤线屏障（已实现）

`pnpm analyze:flood` 默认改用**相对口径**：水位以"较基准水面（序列起始水位 23.93 m）的抬升量"表达，地面用 DEM 原始高程，输出上下界：

```bash
pnpm fetch:levees   # 取 OSM 堤线（92 条，仅位置、无堤顶高程）
pnpm analyze:flood            # 默认相对口径
pnpm analyze:flood --frame=absolute --offset=5   # 绝对口径 / 指定偏移做敏感性
```

相对口径把"基准零点"问题换成了"基准水情"问题：淹没边界只依赖 DEM 内部的"地面−水面"高差（这部分可靠），不确定性从 ±5~9 m 降到 ±1~2 m（DEM 成像时的水情未知）。但**基准零点仍然是待标定量**——实测证据如下：

1. 三套独立 DEM（SRTM / GLO-90 / FABDEM）都把长江江面读成 15~17 m，彼此一致；
2. 但 DEM 的**陆地**值相对吴淞可能偏低 4~8 m：把偏移设为 0 时，"常水位 23.93 m"就会淹没堤内平原数千 km²。这在物理上**不算错**——武汉段长江常水位本来就高于堤内低地，全靠堤防挡着——所以真正决定城区淹没范围的是**堤防**，不是 DEM 精度；
3. 结论：绝对面积必须有控制点（堤顶高程或已知地面点）才能收紧；相对口径下的"抬升量 → 淹没面积"曲线是可用的产物。

**但下界还不够紧**：OSM 只有 92 段堤线且覆盖不连续，把它当不可穿越屏障后，水位 27 m 时仍算出数千 km²（水流从堤线缺口绕进来）。要收紧下界，只能补堤顶高程或更完整的堤线数据。

> 关于 DEM 的垂直基准：已查到三份来源背书——Copernicus DEM 官方产品页写明 `Vertical: EGM2008 (EPSG 3855)`、数据由 **TanDEM-X 任务 2011~2015 年**采集；OpenTopography 的 GLO-30 元数据页写明 `Vertical Coordinates: WGS84 Ellipsoid/EGM2008 Geoid [EPSG: 3855]`；FABDEM 论文（Environ. Res. Lett. 17 (2022) 024016，doi:10.1088/1748-9326/ac4d4f）写明重采样到 `COPDEM30 vertical coordinates (EGM2008)`。**所以 FABDEM 的垂直基准是 EGM2008，这条可以写进文档了。**

> **吴淞高程的换算依据**（`docs/吴淞高程系.docx`，词条原文）：吴淞高程以**上海吴淞口验潮站 1871~1900 年实测最低潮位**为基准面；各地实测换算为**宁波 `1985国家高程基准 = 吴淞 − 1.87`、嘉兴 `− 1.828`**，即 **吴淞 ≈ 1985 国家高程基准 + 1.83~1.87 m**；长江流域统一使用的是"七环平差"后的资用吴淞高程，起算基点为镇江 308′ 标点（9.391 m）。词条同时**警告"不能用简单的常差或公式换算"**，差值随地区与时期变化，因此这是带不确定度的口径。

> 叠加 DEM 侧的 EGM2008（Copernicus 官方页 / OpenTopography / FABDEM 论文三处背书），最终取 **吴淞 = DEM + 1.87 m（±0.5 m）** 作为默认偏移（`analyze:flood` 已按此更新），并在自洽性上互相印证：该值使 FABDEM 读到的汉口江边地面 22~24 m 变为 24~26 m 吴淞，与公开认知（江滩 25~27 m）吻合。旧的自动标定 +8.87 m 已证伪（会让地面变 31~37 m），仅保留作对照。**±0.5 m 敏感性实测：27 m 水位下下界从 4205 km²（+1.37 m）到 3844 km²（+2.37 m），波动约 9%。**

> 仍然更严的做法：需要**武汉本地**的 EGM2008 与 1985 国家高程基准控制点（现有 1.87 m 取自宁波/嘉兴，词条已警告不能外推为常差）。

### 真实水系数据（OpenStreetMap）

水域面与岸线不是示意几何，而是从 OpenStreetMap 取的真实水系：

```bash
pnpm fetch:water    # 从 Overpass 取长江武汉段（含汉江下游段）水域面 → scripts/data-src/yangtze-water.json
pnpm build:data     # 派生 public/data 下的水域面、岸线、滩地单元与站点
```

- 取数范围覆盖研究区外扩一圈，裁剪到 `[113.78, 30.12, 114.82, 30.88]`，抽稀容差 12 m；
- 结果是 15 个水体（长江主河道 9 段、汉江 6 段，合计约 306 km²）、16 个江心洲，岸线按河段拆成左右岸；
- **中心线不再手写**：逐段由两岸按相对里程配对生成（过水断面法），滩地单元从真实岸边起算向外分带；
- **站点点位不再按"里程比例"猜**：每个水位站/水质断面在数据表里带一个真实锚点（公开地名/桥梁位置），生成时把锚点投到真实水面边界上——水文站本来就在岸边设站，这样点位既能落在正确河段，也不会漂到岸上或别的河汊；
- 数据来源与许可以 `meta.json` 的 `spatialSources` 字段随数据一起发布：**© OpenStreetMap contributors，ODbL 1.0**；
- `scripts/data-src/yangtze-water.json` 缺失时 `pnpm build:data` 会自动回退到示意几何并给出提示，因此离线也能构建。

几何质量用脚本回归校核（环闭合、江心洲落在外环内、水位站在水面内、滩地内圈贴岸距离、桥梁断面对照、滩地环自交）：

```bash
pnpm verify:data
```

### 坐标系统一与底图纠偏

平台内所有矢量数据、空间分析结果与状态栏读数统一采用 **WGS-84 / 2000 国家大地坐标系**（路网取自 OSM，桥梁为公开整理的真实经纬度）；高德底图瓦片则建立在 GCJ-02 加密坐标系上，两者在武汉段相差 **568~604 m**（方位 115°~120°），直接叠加会出现"岸线与影像对不上"。

处理方式是**只纠偏底图、不动业务数据**：

- `src/core/cesium/gcj02.js`：实现 GCJ-02 ↔ WGS-84 互转（逆变换用不动点迭代，往返误差 1e-8 m 量级）；
- `src/core/cesium/gcjTilingScheme.js`：自定义瓦片方案，请求瓦片时把 WGS-84 位置换算成高德坐标取瓦片索引（保证 `{x}/{y}/{z}` 取到正确内容），贴图时把瓦片范围逆变换回 WGS-84（保证影像落在真实位置）；
- 影像层与注记层共用同一份纠偏方案，因此底图、注记、地形、矢量相互对齐；
- 天地图影像与 ArcGIS 地形本身即为 WGS-84 口径，不参与纠偏。

纠偏不用"统一加固定偏移量"的简化做法：GCJ-02 是与位置相关的非线性加密，偏移量沿河段从 604 m 变到 568 m、方位摆动 5°，固定偏移只能让中段对上、两端露馅。

纠偏效果可回归校核（按瓦片像素衡量，各层级残差均 < 0.5 px）：

```bash
pnpm verify:gcj02
```

> 全部数据均为演示用途，不作为任何决策依据。

可选配置：复制 `.env.example` 为 `.env` 并填入天地图 key（`VITE_TIANDITU_KEY`），即可启用天地图影像与注记；不填则使用高德影像，无需任何密钥。

### 底图清晰度

图层树第一组可以在**高德影像 / 高德矢量 / Esri 影像 /（天地图影像，需 tk）**之间切换，都是无需付费、无需备案的服务：

| 底图 | 最高级别 | 说明 |
| --- | --- | --- |
| 高德影像 | 18 | 默认底图，无需 key；武汉段影像偏旧、分辨率一般（瓦片数据量约为 Esri 同位置瓦片的 1/3） |
| Esri 全球影像 | 19 | 无需 key，与项目已用的 ArcGIS 地形同一服务商；城市区影像更细，WGS-84 口径**不需要纠偏** |
| 天地图影像 | 18 | 需要免费申请的 `VITE_TIANDITU_KEY` |

渲染侧还有三个清晰度开关，都集中在 `src/config/scene.js` 的 `SCENE_DEFAULTS`：

- `useBrowserRecommendedResolution: false`：按屏幕物理像素渲染。Cesium 默认忽略 `devicePixelRatio`，在 125%~200% 缩放的屏幕上底图会被放大、看着发软；
- `maxRenderPixelRatio: 2`：物理像素放大上限，4K/Retina 下兼顾清晰度与帧率；
- `globeMaximumScreenSpaceError: 1.5`（Cesium 默认 2）：调小 → 同一视距请求更高层级的瓦片与更密的地形网格，代价是瓦片请求量与三角形数增加。

另外 `fogDensity` 与 `skyAtmosphere` 会随距离叠加淡雾，远景看着偏"灰"；追求通透可以再调小 `fogDensity` 或关闭 `scene.globe.showGroundAtmosphere`。

### 数据重新生成

`scripts/build-data.mjs` 会读取本地武汉空间数据（默认路径可用环境变量 `SOURCE_DATA_DIR` 覆盖）并输出全部演示数据。若数据源不存在，脚本会跳过桥梁/路网文件并给出提示，其余数据仍可正常生成。

## 七、已知限制与可扩展方向

- 水域面与岸线为 OSM 真实水系（精度取决于 OSM 测绘质量）；滩地淹没单元是沿真实岸线外扩的示意单元，大距离外扩在凹岸有轻微几何折叠（单环 ≤ 4 处），不能用于真实统计。
- 时序数据为模拟数据：接入水情数据库或监测接口时，只需替换 `dataService` 的数据源。
- 未接入 DEM 栅格淹没计算：当前用"滩地单元 + 高程属性"的方式做面积统计，接入 DEM 后可扩展为栅格逐格判定或等高线提取。
- 未做后端、权限与协同：生产平台还需要数据服务、权限体系与运维监控。
