# 面试高频追问与参考答案

## 一、项目与岗位相关

**Q1：这个平台和普通的"三维页面"有什么区别？**
页面是把所有逻辑写在一个场景组件里；平台是让每个功能成为可插拔的模块。我的项目里每个功能都要实现同一份契约（`init(ctx)` / `destroy()`），由注册中心统一挂载与销毁，图层树上的勾选本质上是模块启停。这样加第十一个功能不用改前面的代码，关掉功能也不会留下实体和监听。这也是"平台研发"这个岗位和"前端切图"的分界。

**Q2：为什么选 Cesium，而不是 three.js 或 Mapbox？**
需求是地理坐标下的时空数据表达：需要真实经纬度定位、地形起伏、影像底图、大范围场景与空间分析。Cesium 天生以地理坐标系为核心（WGS84 椭球、地形服务、影像服务、3D Tiles 规范），做量算、剖面、淹没这类分析时不用自己处理坐标转换；three.js 更适合产品级展示和特效，做地理场景要自己补一整套坐标与数据体系；Mapbox 强在二维矢量渲染与路网数据（我确实用它做过武汉路网），但三维分析与地形不是它的长项。三者不是替代关系，我在这个项目里也把 ECharts（二维图表）和场景（三维）结合起来用。

**Q3：你在项目里承担哪些部分？**
从数据到前端全流程：设计数据结构与生成脚本（含降雨—洪水过程的模拟逻辑）、设计平台架构、实现全部模块与 HUD、完成坐标系/高程基准处理与文档。

## 二、架构设计

**Q4：模块契约具体约束了什么？为什么要有它？**
约束四件事：`id/name/group`（注册与图层树）、`layers`（声明图层）、`init(ctx)`（挂载并返回对外 API）、`destroy()`（清理）。有了契约，注册中心才能统一管理启停；有了 `destroy`，"反复开关图层导致内存增长"这类问题才有正解——Cesium 的 entity、primitive、`ScreenSpaceEventHandler`、后处理阶段都不会自动回收，必须显式移除。

**Q5：事件总线和 Pinia 为什么同时用？**
它们解决两类不同问题。状态回答"现在是什么"——当前时刻、当前水位、图层开关，需要被多个面板同时读取并响应式更新，所以放 Pinia；事件回答"刚刚发生了什么"——选中了某个站点、某个分析出了一个结果，是一次性通知，用事件总线广播，谁关心谁订阅。如果用事件传状态，面板刷新时序会变成一场灾难；如果用全局状态传所有通知，状态里会堆满一次性字段。

**Q6：水位在多个地方使用（三维水面、淹没判定、站点着色、状态栏），怎么保证一致？**
只有唯一真值来源：`data.effectiveWaterLevel`，其余全部由它派生。它有两个输入——跟随时间轴取参考站（汉口武汉关）的实测模拟序列，或用户手动设定情景水位。三维水面高度用 `CallbackProperty` 每帧读它，淹没判定和状态栏也读它，所以不存在两套状态打架。

**Q7：时间轴推进时，你重建实体还是更新属性？**
更新属性。站点的颜色、尺寸、标注文本，以及水面高度，都用 `CallbackProperty` 逐帧读取状态，而不是销毁重建实体。重建会让 Cesium 反复创建 GPU 资源，导致卡顿与内存抖动。代价是每帧会有几十次属性求值，但只有二十多个站点，这个开销可以忽略。

## 三、空间数据与坐标

**Q8：屏幕点击怎么拿到经纬度和高程？**
三维场景是画在 canvas 上的，没有 DOM 节点可以点。做法是：相机 + 鼠标位置生成一条拾取射线（`camera.getPickRay`），与地形或椭球求交（`scene.globe.pick`），得到笛卡尔坐标，再转成 `Cartographic` 得到经纬度和高程。选实体则用 `scene.pick` 拿到被点击的图元，再读它绑定的要素属性。

**Q9：距离和面积怎么算的？为什么不用 turf？**
距离用椭球测地线（Cesium 的 `EllipsoidGeodesic.surfaceDistance`），是真实椭球面上的最短距离，不是平面直线；面积用球面多边形公式（Chamberlain & Duquette），本质是球面超额。验证方式：赤道附近 0.01°×0.01° 的方格，球面公式结果 1.0653 km²，与平面近似 1.0677 km² 相差 0.23%，落在预期范围内。turf 当然可以用，但这两个公式不到三十行，自己实现能少一个依赖，也更能说明我理解算法本身。

**Q10：高程基准是怎么处理的？**
这是个真问题。站点的水位、滩地高程、警戒水位都来自水文口径，用的是吴淞高程；而地形服务返回的高程是大地水准面/椭球口径。这两套数直接比较会出错。我的处理是：**所有分析和阈值判定统一在吴淞高程下完成**，只在三维渲染时按固定偏移量换算成场景高程，偏移量集中在配置里并注明是演示取值，生产环境要用基准转换模型或控制点精算。剖面曲线单独标注了它是地形服务口径，要和淹没关系比较时必须先做基准转换。

**Q11：高德底图在国内为什么会偏移，你怎么解决的？**
这是国内三维 GIS 绕不开的坑。高德、腾讯这类底图服务的瓦片是 GCJ-02 加密坐标（俗称火星坐标），而 Cesium、地形服务、OSM 数据都是 WGS-84 口径，同一地点两套坐标在长江武汉段相差 568~604 m、方位 115°~120°，直接叠加就会看到"岸线跑到河道外面去了"。
我的原则是**真值坐标不动，只纠偏底图**：矢量、量算、剖面与状态栏读数全部保持 WGS-84，纠偏只作用在底图瓦片这一层。实现是自定义一套瓦片方案（继承 Cesium 的 `WebMercatorTilingScheme`），两个方向同时改：请求瓦片时把 WGS-84 位置换算成高德坐标再取瓦片索引，保证 `{x}/{y}/{z}` 取到的是正确内容；贴图时把瓦片覆盖的 GCJ-02 范围逆变换回 WGS-84 作为显示范围，影像才会落在真实位置上。影像层与注记层共用同一套方案，两者之间也自然对齐。
我没有用"统一加一个固定偏移量"的常见简化做法：GCJ-02 是与位置相关的非线性加密，偏移量沿河段在 568~604 m 之间变化、方位还摆动 5°，固定偏移只能让中段对上、上下游两端露馅。逆变换没有解析解，我用不动点迭代（3~4 次收敛到厘米级），并写了回归校核脚本，按瓦片像素衡量各层级的贴图残差（全部小于 0.5 像素），同时检查相邻瓦片不留缝、点位被正确覆盖。

**Q12：你的水系数据是怎么来的？为什么不用 OSM 的河道中心线？**
水域面和岸线是真实数据，不是示意几何：我用 Overpass 从 OpenStreetMap 取回长江武汉段与汉江下游段的水域面（`natural=water` + `water=river`，含 16 个江心洲内环），做了裁剪、抽稀（12 m 容差）和按河流归组，一共 15 个水体、约 306 km²，数据许可是 ODbL，署名随数据一起写进 `meta.json`。
有一个坑值得说：OSM 里虽然也有 `waterway=river` 的河道中心线，但它不能用。它在汊道和分汇流处会分叉，按端点拼接时容易顺着支汊走，实测拼出来的线在两岸之间来回横跳、跨度到 20 km，拿它当基准外扩，滩地单元会挂到几百米外的陆地上。所以我的做法是**从水域面反推中心线**：把每个河段的外环按主轴拆成左右两岸，再逐点配对取中点得到本段中心线，站点沿它定位；滩地单元不从中心线算，而是直接从真实岸边向外分带外扩，这样最近一圈与岸线的距离实测是 0 m。
几何质量我用脚本回归：环是否闭合、内环是否落在外环内、水位站是否都在水面内、滩地内圈到岸线的分位数距离、以及用真实桥梁断面做对照。最后一个很有意思：武汉长江大桥主跨两端点本来应该落在两岸，之前被示意河道盖住 138~172 m，换真实水系之后两端点都回到了岸上。

**Q13：淹没分析是怎么实现的？为什么不用 DEM？**
当前实现是"滩地单元 + 高程属性"：把两岸滩地按高程分成四类单元，每个单元带一个高程属性和预先按球面公式算好的真实面积；水位高于单元高程即计入淹没，淹没面积 = 被淹没单元的球面面积之和。它等价于对地形做了一次离散化采样，优点是零栅格数据依赖、结果可解释、性能稳定。
接 DEM 之后的升级路线我清楚：把库区范围划成规则网格，逐格比较 `z < h`，面积 = 满足条件格数 × 格面积，体积 = Σ(h − z) × 格面积；或者从 DEM 提取水位等高线得到闭合范围面。两者都能在这套模块结构里直接替换，不影响其它功能。

## 四、性能与优化

**Q14：场景数据量大了怎么优化？**
分几层讲：数据层按需加载与分级（当前路网就是从三万余条里筛出 800 条主干道，而不是全量加载）；渲染层依赖 Cesium 的 LOD 与屏幕误差；要素密集时用聚合（我课程里做过实体聚合）；把静态要素合并成 primitive 或 3D Tiles，减少 draw call；给标签加距离显示条件 `distanceDisplayCondition`，远处不渲染。此外用帧率与实体数量做监控，先量化再优化。

**Q15：如果要加载倾斜摄影或 BIM 模型（3D Tiles / glTF）？**
3D Tiles 用 `Cesium3DTileset` 加载，重点在瓦片集的空间索引与屏幕误差调参、样式（`Cesium3DTileStyle`）按属性着色、以及点击拾取 `tile.content` 反查属性；glTF 模型用实体或 primitive 加载，注意坐标系（模型本地坐标 → ENU 局部坐标 → 地理坐标）和裁剪/剖切。这些我都作为下一步扩展，因为当前项目的重点是时空数据表达与分析工具。

## 五、数据与真实性

**Q16：你的数据是真的吗？**
分三类讲：水域面、岸线与桥梁是真实数据——水域面与岸线取自 OpenStreetMap（ODbL 许可，署名写在数据与文档里），桥梁是真实坐标与公开简介；站点用的是真实站点名称、河段位置与公开的警戒水位；时序数据是按水文规律模拟的，滩地淹没单元是沿真实岸线外扩的示意单元（高程为演示取值）。界面上和文档里都明确标注演示口径。这样处理是为了不受数据版权与获取周期限制，同时保留真实的业务逻辑：降雨滞后形成洪峰、上游水位高于下游、超警戒触发预警。

**Q17：如果给你真实数据，你需要改哪些地方？**
数据替换层：`dataService` 与 `public/data` 的格式不变即可直接替换；算法升级层：淹没分析换成 DEM 栅格法或等高线法；渲染层：增加 3D Tiles 建筑/倾斜模型；接口层：时序数据从静态 JSON 换成后端接口（前端已经有统一的数据服务，接接口只改一个文件）。

## 六、不足与反思（面试官常问"遇到什么问题"）

**Q18：这个项目最大的不足是什么？**
三点。一是数据精度：水域面与岸线虽然换成了真实水系，但滩地淹没单元仍是沿真实岸线外扩的示意单元、高程是演示取值，不能用于真实统计；二是分析模型深度：淹没只做了高程比较，没有考虑水动力学与堤防作用；三是工程化：没有后端、权限、部署与监控，属于平台的可视化与交互层。我宁愿把边界说清楚，也不愿意把演示数据说成生产数据。

**Q19：如果再给你一个月，你会做什么？**
优先级从高到低：一是接 DEM 把淹没分析升级为栅格法并给出淹没水深；二是增加 3D Tiles 城市与倾斜模型，验证平台的加载与调度能力；三是做数据接口化与历史数据回放（时间轴 + 服务端分页）；四是补性能监控面板（帧率、内存、实体数）与自动化测试。
